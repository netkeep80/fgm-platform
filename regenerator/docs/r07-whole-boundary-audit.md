# Локальная карточка границы одного ObjectDefinition

Этот срез проверяет объявленную границу объекта после существующего source-bound
R07. Он не выбирает истинный объект автоматически и не принимает Stage A.
**StageA NOT_ACCEPTED / PRIVATE_ACCEPTANCE_PENDING** сохраняются даже при
`GEOMETRIC_BOUNDARY_PASS`.

## Что добавлено

В частном каталоге создаются ровно два файла:

- `object-boundary.private.json`: версия гипотезы, состав B1, точные source/fit/model/
  binary SHA, исходная опись частей, выбранных и исключённых из объявления, метрики
  и результаты native Core в 26-соседстве.
- `object-boundary.public.json`: только фиксированные schema/status, количества и
  непрозрачные SHA. Нет координат, названий объекта/dataset, путей, LOFT/спрайтов,
  масок, FGM/OBJ или других игровых байтов. Новое поле частной карточки не появляется
  в публичном свидетельстве автоматически: используется явный allowlist.

Частная карточка и исходные/производные игровые файлы **остаются локальными**.
Не помещать их в публичный GitHub/CI/Pages. В Issue #11 можно разместить только
проверенное публичное свидетельство и текстовый статус независимого разбора.
Каталог результата публикуется атомарно, существующий каталог не заменяется.

## Проверяемое утверждение

1. Manifest, источники, B1, preflight и исполняемые файлы фиксируются в частном
   staging. Оригинальные пути больше не читаются во время replay/описи.
2. Существующий `r07_whole_source_fit.py` выполняется снова с тем же режимом поиска.
   Полные байты его receipt должны совпасть с независимо записанным ожидаемым
   receipt. Проверяются все исходные наблюдения и метрики существующей реализации,
   а не только отдельные скопированные проценты. Алгоритм поиска не меняется.
3. Native R02 даёт размер MAP и реальные TilePart/dataset/record. Native R03 даёт
   контрольные суммы декодированных LOFT-строк для всех присутствующих частей в
   выбранных клетках и halo. Новый MAP/MCD/LOFT decoder не вводится.
4. Halo — объединение всех 26 соседей каждой выбранной клетки за вычетом самих
   выбранных клеток. Existing Core sampler проверяет каждый из 6144 центров в
   каждой halo-клетке для baseline и winner. Клетки вне MAP также проверяются
   геометрически и помечаются `OUTSIDE_MAP` в исходной описи.
5. Ожидаемая занятость **целевой** модели в halo равна нулю. Наличие там другого
   исходного объекта не даёт права включать его геометрию в модель. Части в той же
   клетке, не выбранные B1, также видны в описи как исключённые из объявления.

Только полный нулевой результат даёт `GEOMETRIC_BOUNDARY_PASS` и exit0. Вычисленный
ненулевой halo даёт `REJECTED_HALO_OCCUPANCY`, явно отрицательную карточку и exit2.
Неверные входные SHA/replay/protocol/limits отказывают **без выходного каталога**.

Сосед с той же MCD и теми же LOFT может быть самостоятельным объектом.
`DECLARED_MEMBER` и `EXCLUDED_FROM_TARGET_DECLARATION` обозначают содержание
гипотезы, не достоверную семантическую аттестацию. Все части сохраняют
`semantic_identity: UNRESOLVED`. Идентичность объекта остаётся
`CONDITIONAL_ON_B1_WITNESS_NOT_AUTHENTICATED`.

## Путь применения к настоящим локальным данным

1. Выбрать **один** конкретный объект по исходным данным и видимому контексту карты.
   Сформировать B1-гипотезу, перечислив только его части. Зафиксировать спорные части
   и независимых соседей для последующего человеческого разбора. Не выводить
   принадлежность только из смежности, названия MCD или совпадения LOFT.
2. Выполнить [B1 verification](r06-s2b1-verified-membership.md),
   [source preflight](r07-whole-source-preflight.md), затем
   [source fit](r07-whole-source-fit.md) с SHA-pinned native инструментами.
   Сохранить точные команды/входные SHA. `--axis-fit` при аудите должен совпадать
   с режимом receipt. Нужны 2–8 выбранных клеток и не менее двух исходных наблюдений.
3. Независимо записать SHA **всех байтов** `joint-fit-receipt.json`, включая финальную
   новую строку. Например, `sha256sum joint-fit-receipt.json` либо PowerShell
   `Get-FileHash -Algorithm SHA256 joint-fit-receipt.json`.
4. Запустить новый аудит. Параметры manifest/B1/preflight и четыре инструмента
   исходного fit совпадают с предыдущим запуском. Добавляются R02, Core sampler,
   версия гипотезы и ожидаемый fit receipt:

```sh
python regenerator/scripts/r07_whole_boundary_audit.py \
  --manifest /private/selection-0.json --manifest /private/selection-1.json \
  --verified /private/verified.json --verified-sha256 B1_SHA256 \
  --preflight /private/preflight.json --preflight-sha256 PREFLIGHT_SHA256 \
  --fit-receipt /private/fit/joint-fit-receipt.json --fit-receipt-sha256 RECEIPT_SHA256 \
  --studio-native /local/bin/fgmr-studio-native --studio-sha256 STUDIO_SHA256 \
  --r03-native /local/bin/fgmr-r03 --r03-sha256 R03_SHA256 \
  --whole-build-native /local/bin/fgmr-r06-whole-build --whole-build-sha256 BUILDER_SHA256 \
  --surface-native /local/bin/fgmr-r07-whole-surface --surface-sha256 SURFACE_SHA256 \
  --r02-native /local/bin/fgmr-r02 --r02-sha256 R02_SHA256 \
  --sampler-native /local/bin/fgmr-r06-multicell-sample --sampler-sha256 SAMPLER_SHA256 \
  --hypothesis-version 1 --output /private/object-v1-boundary
```

`*_SHA256` — заменяемые placeholders, не готовые контрольные суммы. В Windows
использовать соответствующие локальные пути и `.exe`. R02 SHA должен совпадать с
зафиксированным B1 provenance. Binaries копируются и хэшируются до исполнения;
изменение оригинального pathname не меняет уже зафиксированную копию.

5. Независимо просмотреть **частную** опись и сопоставить её с исходной картой.
   Объяснить, почему все selected parts — одна сущность, а исключённые части ей не
   принадлежат. Повысить версию гипотезы при изменении состава/трактовки и заново
   получить B1/preflight/fit/audit; старые каталоги не заменять.
6. Открыть тот же native-fit результат в Studio1.20+ по
   [инструкции fitted surface](r07-fitted-surface.md): проверить четыре глобальных
   вида и исходные силуэты/до/после. Связать screenshot/локальную визуальную оценку
   с теми же membership/model/fit SHA. Авторская семантическая/визуальная приёмка
   конкретного настоящего объекта проводится отдельно.

## Воспроизведение без оригинальных ресурсов

После обычной root native сборки:

```sh
ctest --test-dir build/native -C Release -R r07-whole-boundary-audit --verbose
```

Тест переиспользует существующую свободную синтетическую binary-format fixture,
реальные R02/R03/Studio/builder/observer/sampler и полный source-fit replay.
Два объявленных члена и третий независимый сосед имеют одинаковую MCD/LOFT.
Опись различает выбор, но не заявляет удостоверенную истинную принадлежность.
34 halo-клетки дают **208896 центров на модель**; у baseline/winner они пусты.
Отдельный полный solid показывает **3624** внешних занятых центра при расширении,
которое ещё проходит C05 выбранных клеток. Это отрицательная проверка геометрического
гейта, не утверждение, что нынешний bounded search выбирает такой winner.

Тестируются неверные SHA, изменённый/rehashed receipt, source corruption, несовпавший
режим поиска, source/native bindings, область halo, приватность allowlist,
детерминизм и отказ перезаписи. Все прежние source-fit receipt/model bytes сохраняют
свои contracts; общий atomic publisher используется и новым отчётом.

## Ограничения и следующий предметный гейт

- До 8 manifest, 2–8 выбранных клеток, максимум 208 halo-клеток. Accepted sampler
  допускает local coordinates −16…16; если halo выходит за них, аудит отказывает
  `E_BOUNDARY_HALO_SCOPE`. Никакого скрытого обрезания области проверки.
- Проверяются **центры** voxel в одном halo-слое. Это не доказательство непрерывных
  коллизий, watertight швов или скрытой геометрии. Текущий B1/source-fit ограничен
  одной выбранной TilePart на tile. Объекты вне этой границы требуют другого среза.
- Native binary SHA фиксирует исполняемые байты. Соответствие принятому Git source,
  compiler/build environment и воспроизводимость частной сборки проверяются отдельно.
- Точная повторяемость одного source-fit не является независимым геометрическим
  oracle его целевой функции и не доказывает истинность исходных наблюдений.
- Оригинального игрового корпуса в публичном CI нет. Новый отчёт готов для частного
  применения, но **не закрывает private Stage A** без такого прогона и отдельной
  авторской приёмки. Две P3 PR52 — fitted GPU depth/RGB oracle и разнообразие mesh
  fixture — остаются открытыми; этот срез их не переименовывает в выполненные.
- Studio/Worker/RendererSession не меняются; Browser iterative R07 и Stage B —
  последующие самостоятельные задачи. Автоматическая публикация при будущем
  принятом merge по-прежнему проходит весь существующий обязательный CI.
