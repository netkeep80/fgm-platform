# Каталог тактических элементов UFO для Studio

В браузерном сценарии пользователь выбирает корень установленной игры или локальной копии её ресурсов, затем тактический блок и интересующий элемент. Исполнитель сам определяет файлы. Список локальных путей используется как индекс, без обращений к файловой системе или сети. Байты для инспекции нужны только у выбранного блока и его наборов; байты остальных файлов не передаются в Worker.

## Команды

- `catalog-directory` принимает `{v:1, action:"catalog-directory", paths:[…]}`. Ответ `catalog.schema = fgmr-ufo-library/1` содержит `maps`, `terrain`, `loft`, `palette`, `paletteIndex=4` и `tabBits=16` для оригинального UFO. Карта содержит `id`, `name`, `path`, упорядоченные `datasets` и `missing`. `datasets:null` сообщает, что профиль блока неизвестен. Ключи наборов в `terrain` указывают на тройки одноимённых `mcd`, `pck`, `tab`; отсутствующий путь равен `null`.
- `catalog-map` принимает `{v:1, action:"catalog-map", map:"CULTA00"}` после `clear` и передачи файла выбранной карты под идентификатором `map` и её упорядоченных MCD под `ds0`, `ds1`, … через `append`. Ответ `catalog.schema = fgmr-ufo-map-elements/1` содержит размеры `dimensions` и элементы `elements`. Запись содержит `tile`, `part`, `dataset`, `record`, `kind`, `name`, `instances` и `rightHalf`. Координаты и часть можно передать в обычный `r06-cell/1` вместе с файлами из каталога. Временный набор файлов остаётся в состоянии подготовки, поэтому клиент может добавить остальные файлы или очистить его.

Каталог распознаёт оригинальные профили, подтверждённые штатными [правилами местности](https://github.com/OpenXcom/OpenXcom/blob/4a4bae5fa2e5a09282928e84943fc84b093e34ff/bin/standard/xcom1/terrains.rul), [транспортом X-COM](https://github.com/OpenXcom/OpenXcom/blob/4a4bae5fa2e5a09282928e84943fc84b093e34ff/bin/standard/xcom1/crafts.rul) и [типами НЛО](https://github.com/OpenXcom/OpenXcom/blob/4a4bae5fa2e5a09282928e84943fc84b093e34ff/bin/standard/xcom1/ufos.rul). Профили содержат имена файлов и порядок наборов. Ресурсы игры в репозиторий не добавляются. В частности, `TEMP`, `MAP3`, `UFO1B` перечисляются как неопознанные.

Каталог учитывает `MAPS`, `TERRAIN` и два файла в `GEODATA`, игнорируя регистр служебных имён. Относительные пути сохраняются в исходном написании. Ресурсы `GEOGRAPH`, `UNITS` и звук не участвуют в тактическом каталоге. Несколько корней, совпадающие без учёта регистра пути и некорректные относительные пути диагностируются до выдачи привязок.

Имена «Пол», «Западная стена», «Северная стена», «Объект» отражают части клеток. «Дверь», «Дверь НЛО» и «Гравилифт» определяются по полям MCD. Для нескольких экземпляров одной записи каталог отдаёт первый по порядку карты и количество. Отдельно представлены случаи северной стены с разным режимом R05. Собственные имена мебели и иных деталей, которых исходные записи не содержат, этот срез не назначает. Кампания, юниты, целые многоклеточные модели и расширения OpenXcom находятся за пределами текущего `r06-cell/1`.


## Оригинальные миниатюры каталога (кандидат FGMV-STUDIO-004)

Команда `catalog-thumbnails` версии протокола `v:1` принимает локально переданные через `clear/append` четыре ресурса `mcd`, `pck`, `tab`, `palette` **одного выбранного dataset**, а также `dataset`, массив `records` (1–8 уникальных номеров), `frameSlot` (0–7), `tabBits` (16 или 32) и `paletteIndex`. Она возвращает `thumbnails.schema=fgmr-ufo-catalog-thumbnails/1`, dataset/frameSlot, однократную палитру RGB8 и для каждого номера `record,frameId,indices_hex` длиной 2560 символов (32×40). Непригодный кадр получает именно свой типизированный `E_R04_...` без подмены соседних кадров.

Декодирование PCK/TAB, таблицы кадров MCD и палитры использует **ту же C++ `r04::spriteFacts`**, что R06/R05; JavaScript не декодирует формат PCK. Лимиты: не более восьми записей в запросе, 4 МиБ входов и 128 КиБ JSON-транспорта существующего Worker. Команда не запускает R06 и не изменяет состояние реконструкции. Данные об исходных файлах не сохраняются и не передаются в сеть. `rightHalf` относится к отображению R05 на стороне UI (левые 16 столбцов становятся прозрачными), а не к повторному разбору PCK.


## D4-U1 — точные размещения SourcePartRef из R02 (read-only, v1)

Команда `catalog-map` продолжает **без изменений** возвращать `fgmr-ufo-map-elements/1` — сгруппированные типы оригинальных элементов, первый representative `tile` и `instances`. В U1 добавляется **новая, независимая read-only проекция тех же native R02 Facts** для размещений каждого настоящего TilePart:

```json
{"v":1,"action":"catalog-placements","map":"CULTA00",
 "floor":0,"offset":0,"limit":128,"sourceDigest":""}
```

Вызов работает с ранее загруженными локальными `map,ds0,ds1,…`, **тем же порядком MCD, что требует штатный профиль**, и тем же `r02::decode`. Ответ `catalog.schema="fgmr-ufo-map-placements/1"` содержит `map`, `dimensions=[x,y,z]`, `sourceDigest` (hex SHA-256), `floor`, `total` по выбранному этажу, `offset`, `nextOffset` (число или `null`) и не более **128** `placements`. Страницы последовательно перечисляют *фактически присутствующие* TilePart в **порядке бинарных MAP-записей**, внутри записи по частям `floor/west_wall/north_wall/object`. Смещения от нуля, `offset=total` даёт пустую последнюю страницу, `offset>total` — `E_STUDIO_PLACEMENTS_PAGE`. Недопустимые `floor`/`limit`, профиль или необязательная схема запроса дают типизированную ошибку.

Каждое размещение имеет собственный `sourcePartRef=<sourceDigest>/<tileIndex>-<partIndex>`, `tile=[x,y,z]`, `tileIndex` (номер MAP-записи), `partIndex` (0…3), `part`, `sourceIndex` (закодированный **глобальный** MCD индекс), `dataset` (ID упорядоченного набора), `record` (локальный индекс), `rightHalf` для проекции R05, `kind` и `name`, полученные тем же native MCD описателем. **Sprite frameSlot не является partIndex**; оригинальные 32×40 кадры по-прежнему декодируются командой R04 `catalog-thumbnails`. `SourcePartRef` — идентичность **одного исходного размещения**, не `ObjectDefinition`, не фрактальная геометрия, не юридическое свидетельство происхождения UFO.

Хеш строится из доменно-разделённого префикса v1 и **длинно-префиксированных исходных MAP байтов, ID и MCD байтов в порядке штатного профиля**. Это проверка целостности конкретной локальной выборки, **не доказательство подлинности исходных игровых ресурсов**. Первая страница передаёт `sourceDigest:""`; все последующие обязаны возвращать/эхо-проверять точный digest. Чужой digest → `E_STUDIO_PLACEMENTS_DIGEST`. Любая замена файла или каталога обнуляет выбранные ссылки и эпоху Worker. Ранее выданные SourcePartRef не переносятся автоматически на другой digest.

Лимит R02 MAP 64 KiB, входы остаются на существующем Worker; один ответ — максимум 128 размещений, не новая копия полной карты. UI может листать страницы внутри выбранного этажа и выбирать реальное размещение. Существующий R06 получает его **настоящие** `tile` и `part`, R05 и R04 не переопределяются. Карта 50×50, MapBlock composer, выделение объектов по семантике и операции редактирования **в U1 отсутствуют**.

**Обязательная независимая проверка до merge:** полный подсчёт исходных TilePart, одинаковый MCD record в разных координатах → разные `sourcePartRef`, этажи, `rightHalf`, 127/128/129 boundary, ошибочные MAP/MCD/профили, stale input, строгий native/WASM parity, настоящие Chromium keyboard/focus и R04 preselect → R06 selected placement. Никакой PR CI не означает авторскую приёмку и право на автоматический Production release.
