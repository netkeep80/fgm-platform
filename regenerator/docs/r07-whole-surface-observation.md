# R07-S1B1B0 — единая FGM-поверхность нескольких клеток, C05 для всего состава

**Статус:** кандидат, [Issue #58](https://github.com/netkeep80/fgm-regenerator/issues/58), после принятого [R07-S1B1A PR #57](https://github.com/netkeep80/fgm-regenerator/pull/57). `fgmr-r07-whole-surface` — opt-in native C++20 наблюдатель **одного** canonical FGM-пакета в локальном базисе многоклеточного объекта. Он **не** является самостоятельной ObjectDefinition, R07-fit или Stage A acceptance.

## Почему нельзя использовать старый S1A без изменения

Принятый `fgmr-r07-surface` R07-S1A предполагает, что все FGM-пробы принадлежат одной клетке и лежат в интервале `[0,16]×[0,16]×[0,24]`. Но принятый R06-S2B2 хранит **одну** FGM-программу всего экземпляра, где `local_xyz` — координаты клетки относительно B1 anchor. Проба в этой единой программе определяется:

```text
FGM_global(X,Y,Z) =
  FGM.sample_local(local_xyz * (16,16,24) + (X,Y,Z))
```

Для пикселя исходного R05 окно каждой отдельной части по-прежнему строится принятой камерой:

```text
tile_anchor   = r05::tileAnchor(tile_xyz)
sprite_anchor = r05::spriteAnchor(tile_xyz,p_level)
sx = sprite_anchor.x + px + 0.5
sy = sprite_anchor.y + py + 0.5
d  = sx - tile_anchor.x - 16
h  = sy - tile_anchor.y - 20
(X,Y,Z) = (t,t-d,t-d/2-h)
```

Луч ограничивается границами **данной** клетки: `X,Y∈[0,16], Z∈[0,24]`, а проба переводится в единый базис только перед `fgm::Evaluator::sample_local`. Это позволяет сравнивать R04-спрайты отдельных клеточных частей с единой FGM-геометрией. Однако такие клеточные наблюдения **не** являются четырьмя независимыми глобальными 3D-ракурсами и не моделируют межклеточную глубину/окклюзию.

## Вход и строгий C05

Запрос (пример — **схема с заполнителями, не исполняемый JSON**):

```json
{
  "schema": "fgmr-r07-whole-surface-request/1",
  "package": "<canonical local fgm-package/1 string>",
  "package_sha256": "<independently checked SHA256 of exact package bytes>",
  "material": "stone",
  "cells": [
    {
      "tile": [0,0,0], "local_xyz": [0,0,0],
      "reference_rows": "<384 validated R03 uint16 row values>",
      "p_level": 0, "right_half": false
    },
    {
      "tile": [1,0,0], "local_xyz": [1,0,0],
      "reference_rows": "<384 validated R03 uint16 row values>",
      "p_level": 0, "right_half": false
    }
  ]
}
```

Пределы: от 2 до 8 уникальных `tile` и `local_xyz`, однократная привязка клетки; дополнительно у **всех** клеток обязан совпадать один и тот же B1-якорь `tile - local_xyz`, иначе `E_B0_INCONSISTENT_ANCHOR` без какого-либо результата; `local_xyz` по каждой оси [-16,16], `tile` [0,254], `p_level` [0,255], `right_half` boolean, `reference_rows` строго 384 числа [0,65535] в порядке `z*16+y`; FGM-пакет ≤4 МиБ, весь JSON ≤5 МиБ. Один материал с безопасным ASCII-id длиной до 16.

**Сначала** из всех `reference_rows` формируется точная 6144-битная ожидаемая LOFT-маска в порядке Z/Y/X, с X bit `15-x`. Затем уже принятый `fgmr::sample_whole` использует единственный нормативный FGM evaluator и тот же общий локальный базис для проверки **всех** клеток. Это 6144×N независимых центров и проверка материала. При любом различии C05 возвращается exit 2, пустой stdout и строго `R07-S1B1B0: E_B0_C05_ALL_CELLS_MISMATCH\n`; неполный `surface_pixels_xy` не публикуется. Невалидный пакет, SHA, схема, координаты или FGM-native ошибка — отдельный fatal error, **не** разрешённый кандидатный C05-reject.

Лишь после всех hard gates исполняется непрерывная R05-сэмплирующая проекция. Как и принятый S1A, она использует pixel centers и конечный шаг ≤0.125 вокселя, не заменяет `r05::projectLoft` и не утверждает обнаружение всех тонких элементов. Максимум 200 000 ray samples на клетку.

## Выход и граница доказательства

Версия `fgmr-r07-whole-surface-observation/1`: `model_sha256`, материал, `c05.checked=6144×N`, `c05.match=true`, `raster.algorithm=r07-whole-cell-center-rays/1`, а для каждой клетки — `tile/local_xyz`, SHA 384 reference rows, C05 count, surface pixel coordinates, SHA predicted mask, ray count и probe count.

C05 равенство проверяется **относительно переданных rows**, а не доказывает происхождение rows из игры или истинность внешнего B1-witness. Перед практическим использованием требуется accepted S1B1A source preflight, локальная нативная R03 проверка и зафиксированные SHA-256 каждого источника. Этот срез сам не считывает MAP/MCD/PCK/TAB, не подбирает FGM-параметры, не пишет исходные изображения и не создает успешного `StageAReceipt`.

## Независимая синтетическая проверка

В `tests/test_r07_whole_surface.py` задаются два аналитических куба в общем базисе с центрами (8,8,12) и (24,8,12). Полуразмеры 3.51 и 4.49 отличаются, но все **12288 LOFT-центров** сохраняют одинаковую занятость (6144×2). Каждый ракурс клетки имеет аналитически рассчитанные пересечения луча с шестью плоскостями, без вызова FGM или native ray tracer; для каждого куба ожидается 148 против 244 пикселей. Мутант с игнорированием `local_xyz` должен провалить второй аналитический оракул/общий C05. Негативные кейсы включают неправильную вторую маску, повреждение первой, подмену геометрии второго узла, неверный SHA, дубли координат, неправильные размеры строк, схему и материал.
