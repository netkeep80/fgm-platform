# R02-S1 — декодирование MAP/MCD в проверяемые исходные факты

## Цель и архитектурная граница

R02-S1 извлекает **наблюдаемые исходные факты** из бинарных MAP и MCD без догадок о качестве 3D-геометрии, материале поверхности и художественной реконструкции. Программа не создаёт FGM-0, не вычисляет LOFTEMPS, не открывает PCK/TAB и не загружает данные игры в GitHub. Для CI создаются только собственные временные искусственные файлы.

Существующий R12 остаётся структурным инспектором. Новый независимый C++20 `fgmr-r02` использует явные локальные файлы, ограниченные 16 МиБ на ресурс, и выводит JSON **только в stdout**; в сообщениях и фактах отсутствуют исходные пути. Это локальный ограниченный интерфейс, а не упрочнённый R12-обход каталогов: защита от подмены родительских каталогов между проверкой и открытием (TOCTOU) здесь не заявлена.

Контракт и происхождение проверки [план Platform](https://github.com/netkeep80/fgm-platform/issues/15).

## Подтверждённый исходный формат

Первичные файлы OpenXcom зафиксированы на снимке `OpenXcom/OpenXcom@4a4bae5fa2e5a09282928e84943fc84b093e34ff`. Их исходники используются как проверяемое описание формата, **код GPL не копируется**.

- `BattlescapeGenerator.cpp::loadMAP` (строки 1560–1659): первый байт MAP — `Y` (length), второй — `X` (width), третий — `Z` (height). Размер файла строго `3 + 4·X·Y·Z`. Четыре байта каждой ячейки: `floor, west_wall, north_wall, object`. Индекс X меняется быстрее Y; этажи идут от `Z−1` к нулю.
- `RuleTerrain.cpp::getMapData` (строки 175–198): ноль в байте части означает отсутствие. Ненулевой глобальный индекс относится к конкатенации MCD-наборов в указанном порядке; конверсия в локальный индекс выполняется последовательным вычитанием размеров предыдущих наборов **без арифметического сдвига на единицу**. Некорректный глобальный индекс наш декодер отвергает, не подменяя BLANKS.
- `MapDataSet.cpp::loadData` (строки 105–153, 165–247): каждый MCD содержит ровно 62 байта; `Frame[8]` — 0–7, `LOFT[12]` — 8–19, `ScanG` little-endian — 20–21, флаги дверей/стен/LOS — 30–37, TU — 39–41, броня — 42, `Die_MCD` — 44, `Alt_MCD` — 46, `T_Level` — signed byte 48, `Tile_Type` — 53. Остальные подтверждённые поля документированы в Issue, а неизвестные байты остаются в исходном `raw_hex` без выдуманной интерпретации. Относительные `Die_MCD` и `Alt_MCD` действуют внутри **одного** MCD-набора.

## Нормализованный формат

`fgm-regenerator/map-mcd-facts-v1` в JSON содержит:

- `map.header_yxz` и `map.dimensions_xyz`, массив `map.tiles` в точном физическом порядке файла. Каждый тайл содержит `record_index,x,y,z` и массив из четырёх `parts` с неизменяемыми `source_index`; у ненулевого байта также `dataset` и `local_index`.
- `datasets` в порядке исходных параметров CLI, с `id`, `record_count` и точным `raw_hex` каждой 62-байтовой MCD-записи. Отдельно выдаются `frame`, `loft`, `scan_g`, TU, флаги, броня, `die_mcd`, `alt_mcd` и другие поля, подтверждённые исходным структурным описанием OpenXcom.
- Ни один координатный или пространственный индекс не выводится по художественному изображению. Порядок четырёх частей — не то же самое, что поле `Tile_Type` в MCD: `Tile_Type` сохраняется как отдельное наблюдение.

JSON сериализуется детерминированно; round-trip синтетического MAP восстанавливается по заголовку и последовательности четырёх `source_index`, а MCD — по `raw_hex`, включая неизвестные байты. Это проверка сохранности информации, не вывод о корректности будущего меша.

## Запуск и проверка

После `cmake -S . -B build` и `cmake --build build --config Release`:

```powershell
.\build\Release\fgmr-r02.exe --map "C:\local\synthetic.MAP" --mcd "FIRST=C:\local\first.MCD" --mcd "SECOND=C:\local\second.MCD"
```

`--mcd` повторяется в точном порядке набора в исходной игре. Путь может указывать на локальные пользовательские ресурсы, но **не копируйте stdout такого запуска в публичный Issue или CI**: JSON содержит точные MCD-байты, то есть потенциально исходные игровые данные.

Проверка CI: `python tests/test_r02.py <путь-к-исполняемому-файлу>` запускает 23 теста на искусственных наборах: оси/этажи, четыре части, конкатенация нескольких MCD, строгая семантика нулевого ID, точные байты, порядок кадров и LOFT, signed-offset, round-trip через JSON, воспроизводимость, ошибки размерностей, выравнивания, ссылок/бронезащиты, недопустимые идентификаторы и пути. Прогон выполняется на Ubuntu и Windows рядом с R12 и R01.

## Границы обязательств

`FGMR-MAP-001` — кандидатное требование: `accepted:false/current:false/published:false` до отдельного решения автора. R02 не моделирует физические поверхности, коллизии, динамику дверей, объединение карт в поле боя, анимацию, атлас кадров и алгоритмический FGM; это последующие R03–R06. Синтетические данные получены самостоятельно, никаких оригинальных бинарных файлов в проекте или CI нет.
