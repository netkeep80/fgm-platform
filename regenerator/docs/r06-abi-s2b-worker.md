# R06-ABI-S2B — построение целого объекта в Studio Worker

[Задача регенератора #43](https://github.com/netkeep80/fgm-regenerator/issues/43) · [Общий сборщик S43-S2A](r06-abi-s2a-builder.md) · [Нативная выборка C05](r06-abi-s1-sampler.md)

Действие `start` с алгоритмом `r06-whole-build/1` запускает тот же C++20-сборщик в native Studio и Emscripten Worker. Клиент заранее загружает локальные байты свидетельства B1 и снимков R03 через существующее действие `append`. Параметр `offset` задаёт смещение в байтах, `hex` содержит следующую порцию до 32 КиБ. Клиент получает ожидаемые SHA-256 из доверенного локального источника. Сборщик проверяет хеши, структурные связи и соответствие C05. Первичное свидетельство проверяет B1, а происхождение снимков от MAP/MCD/LOFTEMPS устанавливается до вызова.

## Запуск и выгрузка

В объекте `spec` передаются `algorithm`, закреплённый `coreRevision`, `budget`, `sourceBindings` и `parameters`. Для двух снимков пример имеет вид:

```json
{
  "v": 1,
  "action": "start",
  "spec": {
    "algorithm": "r06-whole-build/1",
    "coreRevision": "ba91a5e96d9f4f9580c9b2e9a9460b97acb7f01b",
    "budget": 12288,
    "sourceBindings": {
      "receipt": {"file": "receipt", "sha256": "<expected B1 SHA-256>"},
      "lofts": [
        {"file": "loft-a", "sha256": "<expected R03 SHA-256>"},
        {"file": "loft-b", "sha256": "<expected R03 SHA-256>"}
      ]
    },
    "parameters": {"material": "stone"}
  }
}
```

Идентификаторы должны ссылаться ровно на все загруженные файлы. Успешный `start` присваивает новый `runId` и передаёт загруженные байты запуску. Неуспешный `start` оставляет их доступными для исправления привязок или `clear`. Бюджет равен 6 144 центрам на клетку. Пока запуск активен, операции загрузки и очистки отклоняются. `pause`, `resume` и `cancel` применяются между командами. `step` атомарно завершает вычисление, поэтому отмена должна поступить до его начала.

При `COMPLETED` команда `finalize` возвращает в `result.build.artifacts` имя, размер и SHA-256 каждого из пяти артефактов. Команда `read-build` с тем же `runId`, `artifact` и `offset` возвращает поле `chunk`:

```json
{"v":1,"action":"read-build","runId":1,"artifact":"preview.obj","offset":0}
```

Поля ответа `chunk.artifact`, `chunk.offset`, `chunk.bytes` и `chunk.eof` описывают одну порцию. `bytes` — строка ASCII, которую клиент сохраняет как байты после разбора JSON. Смещение, равное размеру артефакта, даёт пустую строку с `eof=true`. Результат можно повторно прочитать до следующего успешного `start`; устаревший идентификатор получает `E_STUDIO_RUN`. Ошибка вычисления завершает запуск в `FAILED`, а выгрузка доступна только после успешного завершения.

## Границы профиля Studio

| Ресурс | Верхняя граница |
| --- | --- |
| Клетки / часть / материал | 2–8 клеток, одна часть на клетку, материал до 48 символов |
| Вход | 64 КиБ на файл, 256 КиБ суммарно |
| Вычисление | 128 блоков, не более 49 152 центров C05 |
| Выход | До 768 КиБ для OBJ, до 1 МиБ артефактов суммарно |
| Порция выгрузки | 32 КиБ до JSON-кодирования |

Профиль ABI ограничивает вызов на native Studio и WebAssembly одинаково. Превышение лимита даёт `E_STUDIO_LIMIT`; несовпадение ожидаемых SHA-256 и ошибки сборки дают `E_STUDIO_BUILD`. Нативный CLI сохраняет пределы S43-S2A.

CI сравнивает пакет, срезы, OBJ, отчёт и свидетельство с нативным CLI. Четыре основных файла также сверяются с Python B2. В Node Worker и Chromium повторяется тот же протокол, включая отмену, повторный запуск, испорченное свидетельство, устаревший `runId`, превышение лимита и многопорционную выгрузку. Подключение к опубликованной Studio относится к [Renderer #38](https://github.com/netkeep80/fgm-renderer/issues/38).
