# S03 — перенос требований в корень монорепозитория

**Этап:** [Issue #6](https://github.com/netkeep80/fgm-platform/issues/6). Нормативный источник самого переноса — `FGMP-MIG-REQ-001`. Этот документ и JSON-реестр объясняют преобразование, но не подменяют Requirements и решение автора.

**После перехода к S04:** этот протокол проверяет исторический принятый S03 HEAD `4c46d0f3aa2176a8d63448c01df55614ce169956`, а текущий срез проверяется отдельно по [правилам S04](core-integration.md). Исторический checker и реестр сохраняются побайтно.

## Исходная база и полнота

База Platform: `495ebf1a28d8563a0fd6681aadb2cc77d76cb696`, дерево `de224a85b0957ca1de1e26d593a3c1ee099f85e2`. Это проверенный merge S02, содержащий точные снимки из `docs/source-snapshots.json`. Исходные репозитории используются только для чтения.

| Ветвь | Старый каталог | Новый каталог | Число ID |
| --- | --- | --- | --- |
| Ядро Core | `core/requirements/` | `requirements/core/` | 11 |
| Регенератор | `regenerator/requirements/` | `requirements/regenerator/` | 31 |
| Рендерер | `renderer/requirements/` | `requirements/renderer/` | 31 |
| Всего | Три исходных ветви | Три нормативных ветви | 73 |

Дублирующих нормативных копий в модулях после переноса нет. Два корня каждой исходной ветви сохраняются самостоятельными: новые `derives_from` между модулями не изобретаются. С тремя прежними FGMP и новым требованием переноса получается 77 канонических требований. Все ссылки между requirement ID сохраняются без изменений.

## Правила преобразования и владения

| Ссылка | Преобразование | Текущий смысл |
| --- | --- | --- |
| ID и `normative` | Без изменений | Сохранение содержания требования |
| Артефакт модуля | `path` → `<module>/path` | Владелец — исходное предметное требование |
| Артефакт внутри `requirements/` | `requirements/path` → `requirements/<module>/path` | Единственный канонический файл |
| `implemented_by` workflow в трёх `*-GOV-001` | `.github/workflows/repo-guard.yml` | Общий действующий compiler принадлежит также FGMP-PROJECT-000 |
| Остальные исходные workflows | `<module>/.github/workflows/...` | Исторические файлы; GitHub их не запускает из вложенного каталога |
| Проверяющая программа в constraint | Тот же префикс модуля | Сохранение точного verifier |
| Ключ `execution:path` | `execution:<module>/path` | Сохранение связи с преобразованным verifier |
| `derives_from`, `requires`, `depends_on` на requirement | Без изменений | Сохранение независимых ветвей и зависимостей |

`artifact_path_map` и `execution_key_map` каждого ID в JSON задают точную таблицу old→new. Digest полного набора relations и constraints позволяет проверить остальные поля: activation, scope, metric, predicates и порядок не меняются. Сборки, предметные workflow и внутренняя документация модулей адаптируются в S04–S06; существование перенесённого `implemented_by`/`verified_by` не доказывает исполнение теста или готовность продукта.

## Нормативная идентичность и lifecycle

Semantic digest вычисляется по тому же правилу, что в RepoGuard v6.0.1: SHA-256 канонического JSON нормативного значения. Для этих 73 строк это SHA-256 JSON-строки UTF-8; пробелы внутри нормативного текста не удаляются. Дополнительно сохраняются исходный Git blob и SHA-256 исходных байтов файла. Старый и новый semantic subject содержат одинаковые ID/digest и разные repository. Старый Git permalink не является приёмкой нового субъекта.

Реестр сохраняет lifecycle каждого источника отдельно. У 15 источников `accepted=true,current=true,published=false`, у 58 — все флаги false. У всех 73 новых субъектов до отдельного решения автора флаги false. Поэтому 15 lifecycle различаются намеренно, 58 совпадают. Это состояние кандидатов в текущем Git-снимке; исторические приёмки, включая приёмки продуктов с исходными false-флагами, остаются в принятых provenance registries. Перенос не отменяет и не дополняет старые решения автора.

Независимый аудит и явная приёмка точного HEAD/TREE являются отдельными gates. Успешный compiler не выдаёт авторскую приёмку и не меняет lifecycle. Если позднее потребуется изменить флаги файлов, это отдельное нормативное изменение с собственным аудитом.

## Исторический импорт S02

`docs/source-snapshots.json`, список 305 путей `docs/source-snapshot-resources.json`, исходный checker и его тесты сохраняются побайтно. Checker S02 запускается на принятом import HEAD `faff85c3683a7dd87026796bf33ad11ac6d22b33` и его единственном BASE `9a1b41b7050ee2342d247f8d43ce5e3977de2ee6`. Современный HEAD должен происходить от проверенного merge S02; его дерево модулей уже не обязано совпадать с дорефакторинговым деревом.

У FGMP-MIG-SNAPSHOT-001 единственное изменение связи: исторический список ресурсов становится `documents`, а не `requires` с `collection:true`. Нормативная формулировка импорта неизменна. Общая коллекция не обосновывает актуальные ресурсы: все 232 оставшихся файла модулей покрываются предметными требованиями. Иначе исчезновение `verified_by` могло бы скрываться за общей import authority.

## Воспроизводимые проверки

```sh
npm ci --ignore-scripts --no-audit --no-fund
node --test tests/bootstrap.test.mjs tests/requirements-migration.test.mjs
node scripts/check-bootstrap.mjs
python -m unittest discover -s tests -p test_source_snapshots.py -v
python scripts/check-source-snapshots.py --head faff85c3683a7dd87026796bf33ad11ac6d22b33 --base 9a1b41b7050ee2342d247f8d43ce5e3977de2ee6
node scripts/check-requirements-migration.mjs 4c46d0f3aa2176a8d63448c01df55614ce169956
node scripts/verify-requirements-transition.mjs
```

Для последнего шага `.rg-transition` должен содержать RepoGuard на exact commit `74db97791e6da8a75287164f0d0b41579108f114` с установленными runtime dependencies. CI получает этот коммит отдельно; исходники compiler не модифицируются. Положительный переход — реальный S02 BASE→S03 HEAD; отрицательные коммиты изолированы во временном клоне. Удаление всех `verified_by` FGMC-EVAL-001, замена пути evaluator на отсутствующий и новый не обоснованный ресурс должны дать typed `unjustified_resource`. Дополнительные тесты отвергают нормативный drift и подмены реестра, lifecycle, ID, constraints и исходных байтов.

Проверки S03 работают на Linux и Windows. Свежий required RepoGuard отдельно проверяет фактические BASE/HEAD PR; сохранённый S02 oracle не заменяет его.

## Методика проверки требований

Использованы принципы Вигерса и Битти, «Разработка требований к программному обеспечению», третье издание, главы 11, 17, 27 и 29: единственная нормативная запись, постоянные ID, проверяемость, двусторонняя трассировка, контроль baseline и явное управление изменениями. В этом срезе улучшение формулировок старых требований запрещено: найденные смысловые недостатки оформляются отдельно, чтобы не смешивать перенос и изменение содержания.
