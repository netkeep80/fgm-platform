# S3-S2B — реальный поток BuildWholeObject → RendererSession

**Статус:** реализационный кандидат. **Задача:** [Renderer #46](https://github.com/netkeep80/fgm-renderer/issues/46). **Предшественник:** принятый S3-S2A, PR #45. Публичная Studio 1.22 на этом этапе не заменяется.

## 1. Причинная цепочка

Тест `tests/renderer-session-wasm.browser.mjs` принимает только собственные синтетические входы из двух или четырёх клеток. В действительном Chromium он создаёт модульный Worker из закреплённого `build/pages-studio/engine/worker.mjs`, собранного действующим Pages workflow из принятого Regenerator по `studio/engine-lock.json` (версии Core и Regenerator также сопоставляются с манифестом). Исходные JS/WASM-байты дополнительно проверяются на совпадение с SHA-256 манифеста.

Вызовы Worker проходят через **реальный** протокол `clear → append → start(r06-whole-build/1) → step → finalize → read-build`. Для каждого из пяти полученных артефактов сверяются заявленные размеры и SHA-256 **возвращённых WASM-байтов**. Структура `model.fgm.json`, `slices.json`, `report.json`, `input-proof.json`, доказанный объём C05-проб (`6144 × число клеток`), контрольные хеши отчёта и ограниченный смысл проверенного происхождения сверяются перед передачей байтов.

`RendererSession` получает **те же** точные `model.fgm.json` и `preview.obj` в `SceneLoadRequest`. Он независимо проверяет их фактические SHA-256, связывает mesh с исходным пакетом и визуализирует единый объект Canvas2D. Клеточные привязки выводятся из локальных координат `SliceByCell` как диагностическая разметка, а не как отдельные модели. Отдельной реконструкции B1/R03 на JavaScript нет.

## 2. Обработка недоверенных данных и отрицательные проверки

Ограничения S3-S2A сохраняются: 1 МиБ на blob, не более 2 МиБ на загрузку, независимое копирование `Uint8Array` до первого `await`, отказ для `SharedArrayBuffer` и недостоверного C04 identity. В браузерном тесте исходные массивы меняются сразу после начала `loadScene`, затем проверяется успешный кадр из скопированных данных; отдельно порча фактических WASM-байтов модели или OBJ, неверная связь mesh/package и несуществующий ключ модели должны отвергаться.

Принята **политика fail-closed для прежних пикселей**: `loadScene` до валидации, `setView` до валидации и `dispose` синхронно очищают опубликованный Canvas. При отсутствии нового допустимого кадра старое изображение не остаётся на экране. Тесты проверяют очистку после каждого отрицательного сценария, после неверного вида и после уничтожения сессии. Отмена текущего кадра без смены сцены или вида не требует очистки уже актуального изображения.

## 3. Три различных идентичности

`geometryCacheKey` определяет только повторное использование собственно mesh: исходный package SHA, mesh SHA, версию алгоритма, параметры, seed и depth. `sceneCacheKey` дополнительно связывает локальные клеточные привязки, идентификатор и ревизию экземпляра, его перенос и поворот. `presentationCacheKey` дополнительно учитывает камеру, профиль, viewport и выделенную клетку. **Сами кэширующие хранилища не реализованы**: этот этап утверждает только раздельные ключи и отрицательные тесты их конфликтов. Эти хеши не являются доказательством C04-семантики или коллизий.

## 4. Ограничения доказательства

Выполняется настоящий C++20/WASM Builder и Canvas2D RendererSession **в одном Chromium**, но только на двух собственных синтетических конфигурациях 2×1 и 2×2. Браузерный тест не использует файлов игры, не публикует их и не изменяет существующую UI-реализацию `studio/whole-ui.mjs`. Модульные тесты и negative Chromium не доказывают семантическую корректность B1/R03 поверх локальных реальных входов. Подтверждена транспортная целостность, связывание, C05-отчёт принятого источника, но не независимая повторная проверка C04/C05 в Renderer.

WebGPU, восстановление потерянного GPU-устройства, предельные восемь клеток и переход Studio либо игры на общий RendererSession **не реализованы**. Эти ворота остаются следующими самостоятельными срезами. Долг Pages synchronize BASE вынесен отдельно в [Renderer #43](https://github.com/netkeep80/fgm-renderer/issues/43).

## 5. Выпуск

CI `studio-pages.yml` выполняет новый Chromium-тест **после** сборки закреплённого WASM и проверок существующей Studio. В Draft PR публикация Pages не производится. RepoGuard v6.0.1 и отдельный независимый READ-ONLY аудит на exact HEAD/TREE обязательны. Кандидат `FGMV-SESSION-003` сохраняет `accepted:false,current:false,published:false` до самостоятельного нормативного решения; авторское принятие PR не меняет lifecycle автоматически.
