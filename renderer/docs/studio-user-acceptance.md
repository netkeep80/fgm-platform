# Пользовательская задача и критерии приёмки Studio UFO

## Назначение и нормативная принадлежность

Нормативный источник требования — [`FGMV-USER-001`](../../requirements/renderer/FGMV-USER-001.rg.yaml). Этот документ описывает наблюдаемые критерии его приёмки, способы проверки и границы свидетельств; он не создаёт вторую нормативную формулировку. Действующее составное техническое требование [`FGMV-STUDIO-003`](../../requirements/renderer/FGMV-STUDIO-003.rg.yaml) выводится из пользовательской задачи, не отменяется и сохраняет кандидатный жизненный цикл. Детальную атомаризацию технических требований проводить отдельным решением: документ сам по себе не изменяет статусы требований и не утверждает полноту тестов.

Продуктовый смысл: пользователь с локальными ресурсами собственной установки UFO: Enemy Unknown / X-COM: UFO Defense может выбрать **папку игры → тактическую карту → именованный элемент → реконструкцию R06 → просмотр R05 и экспорт**, не разбирая вручную MAP/MCD/PCK/TAB. Восстанавливается **один представительный экземпляр одной статической части**; интерфейс показывает число экземпляров данного типа, но не реконструирует все их экземпляры. Автоматический режим использует первый кадр и материал `stone`. Источником семантики остаётся принятый нативный исполнитель из модуля [`regenerator/`](../../regenerator/), собранный в WASM Worker из общего checkout Platform.

## Сценарий

**Предусловия:** современный браузер с File API и поддержкой WASM Worker; локальная папка установки игры, включающая соответствующие ресурсы; для сквозного успешного сценария — поддерживаемая карта с полным набором. Локальный прогон основного потока на оригинальном комплекте подтвердил выбор элемента и завершение R06 с проверкой C05 на 6144 центрах. Запись о прогоне находится в [план Platform](https://github.com/netkeep80/fgm-platform/issues/15). В CI используется синтетический комплект.

1. Пользователь выбирает папку игры. Приложение показывает тактические карты и указывает неизвестный профиль либо недостаточные ресурсы.
2. Пользователь выбирает доступную карту. Нативный каталог разрешает порядок наборов и именованные типы элементов.
3. Пользователь выбирает элемент. Интерфейс сообщает тип, стабильную исходную идентичность и число экземпляров.
4. Пользователь запускает реконструкцию. R06 использует выбранный снимок байтов MAP/MCD и необходимые файлы LOFT/PCK/TAB/палитры, проверяет C05 и возвращает FGM/OBJ/отчёт/свидетельство.
5. Пользователь переключает виды Original, Reconstructed, Overlay, Difference, Collision и диагностический OBJ и при необходимости сохраняет результаты локально.
6. При смене выбора или Cancel ранее полученный результат и незавершённые ответы становятся недействительными. Ручные привязки находятся в расширенной диагностике; свободный синтетический пример доступен независимо от игрового комплекта.

## Дополнительный сценарий целого объекта — кандидат STUDIO-S3-S1

Отдельная панель `FGMV-WHOLE-001` (ещё не принятое нормативное требование) принимает готовые локальные B1 receipt/R03 snapshots с SHA-256 из независимо зафиксированного локального источника, собирает одну статическую 2–8-клеточную FGM-модель в принятом WASM `r06-whole-build/1`, показывает единую поверхность OBJ и производные `SliceByCell`. Она не заменяет сценарий каталог → выбранный элемент → single-cell R05/R06 и не доказывает первичное происхождение B1/R03 по одному SHA.

Кандидат AC-13: пакет Pages на exact HEAD проходит реальный Chromium whole-object 2×2, локальный File API 2×1 с 10 внешними гранями, отказ при неверном SHA, Cancel/stale, возврат к одноклеточному режиму. До чтения любого File API файла проверяются количество, имена, непрерывные LOFT-индексы, размеры до 64 КиБ и суммарный предел 256 КиБ; негативные Chromium-тесты проверяют отсутствие вызовов `File.arrayBuffer()` для отклонённого набора. После отдельного принятия и слияния проверять те же артефакты и доступность whole-object уже по публичному HTTPS. Связанные исходники: `studio/whole-ui.mjs`, `tests/studio-s2a.browser.mjs`, `tests/studio-pages.live.mjs`, `docs/studio-whole-object-ui.md`.

## Управление принятием и границы

Кандидаты `FGMV-USER-001` и `FGMV-STUDIO-003` сохраняют `accepted:false, current:false, published:false`. Принятие реализации и коммита PR #31 не является автоматическим принятием нормативных версий требований. Отдельное изменение статусов возможно только после определения общей политики жизненного цикла.

**Известные ограничения:** автоматический тест использует самостоятельно созданный небольшой каталог, а не приватные игровые данные; визуальная правильность художественного результата не определяется одним фактом завершения C05; корректность опубликованного сайта не устанавливается до реального HTTP/Chromium-confirm; нормативное разделение всех обязанностей `FGMV-STUDIO-003` на независимые дочерние требования пока остаётся отдельным срезом.

## D4-U0 — переходная единая оболочка Studio (Draft implementation)

В U0 появились пять рабочих пространств **Источник / Объект / MapBlock / Карта / Мир**, доступная клавиатурой навигация и общий viewport-host. Реальные C++/WASM R04 (исходные миниатюры 32×40 ещё до выбора), R05/R06 и whole-object остаются действующими владельцами данных, Worker, source provenance и RendererSession. В переходном режиме Source сохраняет совместимый доступ к прежним whole-object контролам; вкладка Object предоставляет отдельный контекст. Окончательное разделение Source и Object требует следующих срезов.

MapBlock, Карта и Мир явно помечены **NOT_IMPLEMENTED/RESEARCH_ONLY**: нет нативного SourcePartRef-placement selector (U1), MapBlock editor (U3), Battlescape constructor (U4), глобальной 3D-карты, нового backend или World Lab generation. Смена вкладки не меняет RunSpec и не отменяет Worker. При смене вкладки сохраняются исходная выборка, результат R06 и валидная отдельная whole-модель; владелец whole preview сообщает только о его видимости и самостоятельно обрабатывает отмену/устаревшие кадры.

Реальные Chromium/WASM сценарии U0 проверяют стрелки и фокус вкладок, рабочий R04 picker, исходные R05/R06/whole результаты, скрытие/возврат viewport, размеры 390px, отсутствие иных URL/asset и точное ограничение signed bundle из 9 assets. Фокус будущих сеток SourcePartRef будет протестирован в U1, сеток карты — в U4; эти тесты нельзя засчитывать по синтетическому R2 mock. Это Draft и **не разрешение на main merge/automatic Production**.


## D4-U1 — исходные MAP-клетки и выбор конкретного размещения

Во вкладке **Источник** появляется отдельный, доступный с клавиатуры read-only блок **«Размещения исходных частей · R02»** с выбором этажа Z, координатной сеткой и постраничным просмотром реально существующих TilePart. Каждая кнопка — не нарисованный пример, а настоящее размещение исходной MCD-записи по нативному декодеру R02. У одной и той же записи в двух координатах — два разных `SourcePartRef`.

Щелчок или Enter/Space по части клетки выбирает соответствующий **тип** через уже работающий R04 listbox (без нового PCK/TAB decoder) и сохраняет точные `tile/part` для R06; итоговый report и R05 связан с этими координатами. Стрелки/Home/End позволяют перемещать фокус по кнопкам сетки; при изменении источника прошлые идентификаторы и результаты не должны возвращаться. Смена вкладки без изменения источника не должна стирать выделение. При просмотре соседней страницы без смены источника валидный результат не подменяется. Хеш связывает локальные исходные MAP/MCD, **не удостоверяет происхождение игры**.

Студия остаётся той же: R04 original thumbnail 32×40 до выбора, R05 compare, R06, whole-object и девять подписываемых ресурсов. Новая карта-редактор, MapBlock, объектная семантика и фрактальное масштабирование здесь **не реализованы**. Дублирование whole R06 на вкладке «Источник» — сознательно отложенная косметика U0, а не второй вычислительный модуль. P3-D4-U0-02 (отдельный GPU frame-unavailable статус) также перенесён в пост-функциональный UX-проход. **Ни документация, ни Draft PR не разрешают merge/Pages без отдельного решения автора.**

## D4-U2 — рабочие гипотезы принадлежности (проектный черновик, не Stage A)

В пространстве **«Объект»** можно вручную создавать, переименовывать, удалять `ObjectHypothesis` и добавлять к ним **точные выбранные SourcePartRef**, возвращённые нативным R02 в U1. Каждая часть сохраняется с `sourcePartRef`, `tile=[x,y,z]`, `part`, `dataset`, `record`, привязкой драфта к `mapId/sourceDigest`. Одинаковый тип MCD в двух разных клетках — **два разных размещения**. Подмены R02 через JS, автоматического whole-object builder, семантической `ObjectDefinition` или приёмки оригинального UFO здесь нет.

Допустимые операции — `create/rename/assign/unassign/delete` с порядковым локальным журналом применённых и отклонённых `ChangeIntent`. Дубликат в том же объекте отклоняется `E_U2_DUPLICATE`, присвоение другому — `E_U2_MEMBER_CONFLICT` без потери первого владельца; другие типизированные ошибки `E_U2_SOURCE_MISMATCH/E_U2_STALE_SELECTION/E_U2_BINDING/E_U2_LIMIT`. Ограничение одного черновика: 16 гипотез, 128 исходных частей, 256 записей действий; UI не должен разрастаться без контроля. После замены папки/карты драфт остаётся локально, но виден как **STALE_SOURCE** и не допускает новых присвоений; автоматического перевязывания по одинаковому `record` не существует. «Новый черновик текущей карты» — **явная** замена прежнего, старый драфт можно предварительно скачать.

Кнопка локальной выгрузки создаёт `fgmp-studio-object-hypotheses-draft/1`: идентификатор снимка, гипотезы, ссылки частей, журнал действий и конфликты; объём ограничен 128 KiB. **Только по запросу пользователя**, без браузерного постоянного хранилища, MAP/MCD/PCK/TAB/LOFT байтов и сетевой отправки. Импорт, полноценный StudioProject, Undo/Redo — отдельный U6. Это JSON **наброска**, не официальное авторское свидетельство, не готовая FGM-модель.

Реальный packaged Chromium/WASM regression `STUDIO_D4_U2_MEMBERSHIP_CONFLICTS_EXPORT_PASS` использует живой native `catalog-placements` на 3×11×2 MAP, два разных PartRef одинаковой MCD записи, R04/R06 после выбора, клавиатурную навигацию, конфликт и idempotent duplicate, локальную JSON-выгрузку, смену исходного набора и состояние STALE_SOURCE на одноэтажной 132-part карте; старые U0/U1/whole и 9-asset signed allowlist должны продолжать проходить. В PR нет нормализованной миграции требований, новых runtime/API, сети или Stage A acceptance.



## D4-U3 — библиотека и инспектор исходных MAP-блоков (SCOPE-R1)

В рабочем пространстве **MapBlock** выбирается настоящий шаблон `MAPS/*.MAP` из уже открытой локальной папки игры. Библиотека показывает имя/профиль (`READY`, `INCOMPLETE`, `PROFILE_UNKNOWN`) без выдумывания размеров непроверенного MAP. Для выбранного полного профиля те же нативные `catalog-map` и `catalog-placements` R02 определяют `X×Y×Z`, `sourceDigest`, точные `SourcePartRef`, координаты, часть, набор и запись MCD. Измерения подтверждают **целостность локальных исходных байтов**, но не подлинность игровых ресурсов.

В U3 реализована **2D SOURCE_LAYOUT_2D** — сетка клеток `10×10` или `20×20`, количество исходных частей в каждой, этажи `Z`, выбор клетки и R02-части (включая одинаковый MCD record в разных координатах). Выбранная часть передаётся на вкладку «Источник» только после дополнительной нативной проверки `mapId + sourceDigest + floor + SourcePartRef`: Studio загружает соответствующую страницу исходного R02 (включая последнюю), выбирает совпадающую часть через существующую кнопку Source/R04 и разрешает реальный R06 по её точным координатам. Пустая клетка без выбранной части допускает обычный переход без переноса. При изменении источника, этажа или вкладки во время запроса перенос отменяется. U3 **не** запускает R06 сам и не меняет гипотезы объектов U2 автоматически. Это **не изометрическая исходная графика**, не мозаика PCK/TAB всей зоны и не FGM-модель блока. Размеры вне принятого узкого формата показывают `UNSUPPORTED_U3_SCOPE` без ложного «успеха».

Все страницы этажа до 128 размещений читает один ранее принятый native R02 decoder через тот же локальный WASM Worker; ограничение 16 страниц/2048 частей на этаж, проверка заголовка, порядка, идентичности, координат, `sourceIndex`, дублей и SHA-256. Полный этаж отображается **только после завершения и проверки всех страниц**. При смене файла, MAP, этажа или уходе из рабочего пространства старые DOM-кнопки и поздние Worker-ответы не могут восстановить чужую модель. Исходные данные не отправляются в сеть; экспорт и импорт проекта U6 отсутствуют.

**RMP**: Studio индексирует имена `ROUTES/*.RMP` из той же локальной папки, сопоставляя их с `MAPS/<ID>.MAP` по имени без учёта регистра. UI показывает `ROUTE_FILE_PRESENT_UNPARSED`, `ROUTE_FILE_NOT_FOUND`, `ROUTE_INDEX_UNAVAILABLE` или `ROUTE_FILE_AMBIGUOUS`; никаких чтений байтов RMP, узлов маршрутизации, коллизий или доказанной OpenXcom AI-паритетности. `MAPS/*.RMP` не считается каноническим каталогом маршрутов.

**Проверки:** синтетические 10×10×1 и 20×20×2 с настоящим native R02 в упакованной Studio Chromium/WASM, 1600 размещений/13 страниц, переключение этажей, конфликт имён RMP, отмена ожидающего R02, клавиатура и ширина 390px. Маркеры `STUDIO_D4_U3_NATIVE_20X20_2D_LAYOUT_PASS`, `STUDIO_D4_U3_NATIVE_1600_PARTS_13_PAGES_PASS`, `STUDIO_D4_U3_LAST_PAGE_SOURCE_R06_TRANSFER_PASS`, `STUDIO_D4_U3_NATIVE_10X10_STALE_WORKER_PASS`, `STUDIO_D4_U3_RMP_PRIVACY_NAV_MOBILE_PASS`, `STUDIO_D4_U3_RMP_DUPLICATE_PRESENCE_ONLY_PASS`. Сохранены U0/U1/U2/R04/R06/whole тесты и прежние девять файлов подписанного release-пакета.

**Не реализовано и не принимается этим срезом:** реконструкция целой MapBlock, исходная полноэкранная sprite-мозаика, декодер RMP-графа, Battlescape 50×50 composer (U4), свободный ortho/isometric renderer (U5), StudioProject persistence (U6), оригинальный объект Stage A и DR3 R0. U3 подлежит отдельным независимым проверкам и авторской code/merge/Production приёмке.

## D4-U4 — конструктор карты 50×50 (SCOPE-R2)

Режим «Карта» создаёт только локальный `DRAFT_LAYOUT_2D` из отдельных `MapBlockDefinition` (проверены по реальному нативному R02/WASM) и повторно используемых `MapBlockInstance`. Выберите локальную папку игры, откройте «Карта», выберите MAP и нажмите «Проверить шаблон через R02/WASM». Схема имеет 25 слотов 10×10. Блок 20×20 занимает четыре соседних слота, но остаётся **одним** экземпляром. Нажмите слот, затем «Разместить», «Заменить» или «Удалить». Выбор MAP в конструкторе не изменяет текущие U1/U3 размещения и R06, а переключение MAP в той же папке сохраняет черновик. Смена исходной папки очищает черновик и кэш.

`P3-U4-R2-01`: при полном кэше из 25 используемых определений новый шаблон сначала проходит независимую нативную проверку во временном слоте. Замена затем атомарно обновляет экземпляр и его занятые слоты, удаляя из кэша только теперь неиспользуемое определение. Сбой, отмена или конфликт сохраняют старую карту. Нет оригинального мозаичного изображения, OpenXcom mapScripts/RMP-графа, глобального 3D Renderer, фрактального генератора, игровой совместимости, project persistence и принятия Stage A. SHA-256 подтверждает локальную привязку байтов, но не аутентичность оригинальной игры.


**D4-U4 / независимый аудит PR #68 — P2-U4-01 и P2-U4-02:** нативный MAP с нулём размещённых частей (`catalog-placements.total=0` на проверяемом исходном этаже) не получает `NATIVE_DEFINITION_VERIFIED`: отображается `E_U4_EMPTY_MAP`, действующая схема и кэш сохраняются. Отдельная нативная проверка имеет предельный срок 12 секунд, по истечении которого U4 прекращает запрос, завершает собственный Worker, отображает `E_U4_TIMEOUT` и разрешает повтор без потери уже размещённых экземпляров. Эти ограничения не меняют Source/R06.
