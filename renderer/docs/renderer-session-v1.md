# RendererSession v1 — архитектурный контракт (кандидат)

## Текущее состояние Platform

В принятом Platform baseline main `01ed3162f237090cb8759d27769289eae4ccd4a5` опубликована Studio 1.16. Рабочая реализация находится в `runtime/renderer-session-v1.ts`: WebGPU depth/readback, явный диагностический fallback, SHA/scene/view/epoch и проверки реального WASM/Chromium. Интеграция в whole-object Studio описана в [четырёх глобальных видах](studio-whole-novel-views.md); этот новый срез требует собственного exact-HEAD аудита и авторской приёмки.

Ниже сохранено **историческое проектное описание S3-S1**, включая тогдашние будущие работы. Его формулировки «планируется», «не реализуется» и старый номер отдельной Studio не описывают текущее наличие runtime. Они не являются новой очередью разработки.

## 1. Назначение и принадлежность

`RendererSession` — планируемый повторно используемый слой визуального представления одной сцены для Reconstruction Studio и игрового клиента `ufo-fractal`. Владелец API и будущего backend — модуль [`renderer/`](../) единого [`fgm-platform`](https://github.com/netkeep80/fgm-platform); авторитетная FGM-семантика, C04, C05 и идентичность — его [`core/`](../../core/); получение и подтверждение B1/R03 — его [`regenerator/`](../../regenerator/). Тактические правила, состояние мира и сериализация игры остаются в отдельном GPLv3-проекте [`ufo-fractal`](https://github.com/netkeep80/ufo-fractal). Старые три самостоятельных Git-репозитория более не являются владельцами этих модулей.

Текущая Studio действительно выводит единый OBJ через Canvas2D, а `web/main.ts` использует отдельный WebGPU compute для синтетического пакета. Общего рабочего backend сейчас **не существует**. Опубликованные средства представляют собой разные runtime-пути. В контрактном PR не переносится и не заменяется код этих путей.

## 2. Независимые сущности и идентичность

| Сущность | Владелец и неизменяемый смысл | Меняется независимо от |
| --- | --- | --- |
| `CanonicalPackageRef` | Точные bytes `fgm-package/1` и контентный `packageSha256`; при наличии — **отдельно удостоверенный** C04 identity | камеры, профиля, depth, instance |
| `SceneSnapshotV1` | Версия сцены, набор ссылок на модели, список экземпляров с `instanceId` | текущего вида и отрисованного кадра |
| `WorldPlacement` | Положение экземпляра и четверть-обороты в плоскости XY в координатах `fgm-voxel` | bytes модели |
| `DerivedGeometryV1` | Производный mesh, digest источника, `algorithmId` и версия, parameters hash, seed/depth и mesh hash | C04/C05, LOFT, коллизий |
| `VisualProfileRefV1` | Версионированный идентификатор художественного вида и его digest | семантического материала и столкновений |
| `ViewStateV1` | Камера, viewport, selection, grid и профиль; собственная версия | `SceneSnapshotV1` |
| `FrameOutcomeV1` | Наблюдаемый результат определённой пары версий сцены/вида и epoch | источника FGM |

`packageSha256` относится **только к канонически полученным сериализованным байтам**, а не является автоматически семантическим C04-хешем. `verifiedC04Identity` присутствует лишь при отдельном подтверждении Core. Текущий `report.model_sha256` целого объекта по принятой реализации не повышается до доказанного C04 identity по одному названию поля.

Объект из нескольких клеток загружается как **одна** модель. `SliceByCell` — производный вид общей геометрии, а не право регенерировать независимые модели по клеткам. Смежные, но независимые объекты не склеиваются автоматически.

## 3. Переходы сессии и отказоустойчивость

Типовой интерфейс (см. `contracts/renderer-session-v1.d.ts`) задаёт `loadScene`, `setView`, `renderFrame`, `recoverDevice`, `dispose`; перед фактической реализацией он подлежит отдельному независимому рассмотрению.

- `loadScene` принимает только локальные валидированные bytes и сверяет SHA-256 с объявленным package/mesh digest. Должен выполнить проверку ссылок моделей/экземпляров, версий и ограничений ресурсов; входные bytes копируются либо защищаются от изменения на период асинхронного выполнения.
- При `setView` и `loadScene` сессия увеличивает epoch. `renderFrame` обязан сверять `sceneRevision`, `viewRevision` и `sessionEpoch` как единую причинную пару; устаревший кадр возвращает `status: stale`, **но не публикуется** на экран.
- `abort` и `dispose` сбрасывают незавершённые работы. Потеря устройства даёт `device-lost` и требует управляемого восстановления `recoverDevice`; восстановление не изменяет FGM, только ресурсы backend и epoch.
- Если `WebGPU` или поддержка камеры недоступны, результат — явный `unsupported` либо **разрешённый** диагностический `canvas2d-diagnostic`. Никакого тихого выбора другой семантики или заявления GPU-паритета без сравнения.
- Смена camera, selection, display profile или видимой сетки не изменяет bytes, digest модели, C05, LOFT, коллизии, статус игры и `instanceId`. Профиль геометрических деталей может потребовать нового производного mesh с иным `meshSha256`, но не нового исходного FGM.
- Числовая побайтовая эквивалентность GPU-пикселей **не заявлена**. Будущий S3-S3 должен определить измеримые допуски или независимый CPU-эталон.

## 4. Область только S3-S1

Ветка контракта содержит только этот документ, TypeScript declarations, typecheck-fixture, candidate Requirement и добавление исполняемого typecheck в RepoGuard CI. **Ни одна функция `RendererSession` не реализуется; ни Studio, ни WebGPU, ни C05, ни worker, ни engine lock, ни package manifest, ни Pages workflow не меняются.**

Исполнимый типовой тест проверяет корректного потребителя и запрет смешивания камеры с package ref, подмены C04 identity контентным SHA, неверного `quarterTurnsZ` и успеха на отменённом кадре. Это **контрактно-типовые проверки**, не browser parity, не расчёт C05 и не тест работающего backend.

## 5. Проверяемые границы следующих срезов

**S3-S2 (только после принятия этого контракта):** реализация одного backend для whole-object geometry, явная передача пакета и mesh, контроль capabilities, выбор 2D fallback, device loss и отмена, browser tests на реальном WASM и диагностическая сетка. Сохраняется текущая Studio, пока backend не доказал эквивалентность.

**S3-S3:** один и тот же backend/Session используется двумя consumer — Studio и `ufo-fractal`; обе стороны проверяют stable package identity/C05/LOFT, deterministic geometry recipe, independent object placement и отсутствие влияния камеры/профиля на gameplay authority. Игровой клиент пока не содержит такого runtime — внедрение будет отдельным PR/acceptance.

**P3 остаются открытыми:** пиковая нагрузка восьми клеток Chromium (49152 C05-проб), первичное происхождение B1/R03 и дублированный Core SHA. Ни один из них контрактным срезом не признаётся закрытым.

## 6. Приёмка и выпуск

Нормативный кандидат `FGMV-SESSION-001` с отношениями `derives_from` / `depends_on` / `implemented_by` / `verified_by` / `documents` остаётся `accepted:false,current:false,published:false`. Обязательны exact BASE/HEAD/TREE, RepoGuard v6.0.1, отдельный независимый аудит (в том числе смысла типизированного контракта) и **явное авторское принятие**. Green CI не даёт права автоматически переводить Requirement в accepted/current, merge или заявлять работающий backend.
