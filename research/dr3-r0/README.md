## 3. Проверяемая математическая гипотеза

Независимый глобальный аналитический оракул `O-H` вычисляет пересечение луча с ограниченным параллелепипедом методом интервалов. Исследуемый вариант **отдельно** вычисляет пересечения луча с шестью мировыми гранями, раскладывает попадания в 1, 8 или 64 пространственные области и соединяет результаты по глобальной глубине `t`, затем по приоритету и идентификатору.

**Существенное ограничение:** проверяемый вариант сначала перечисляет грани **глобальных** объектов и только потом раскладывает попадания по областям. Это **не** независимое извлечение FGM-поверхности в клетках, не построение геометрических спрайтов и не сертифицированное отсечение. Поэтому сравнение проверяет порядок композиции ограниченных аналитических попаданий, но **не** производительность RVI или корректность фрактальной геометрии.

Лучевые выборки выполняются только с ортографической камерой, с общей фазой субпиксельной сетки. Девять ракурсов: yaw 0.2/0.6/1.2 радиан и pitch 0.28/0.7/1.03 радиан, 40×40×4 субвыборки на ракурс. Дополнительный базовый ракурс: 48×48×4. Шаг камеры 0.14 мировых единиц на пиксель. Допуск глубины 1e-9; совпадение признака попадания, идентификатора и имени грани — строгое. Нормали, UV, затенение и реальный глобальный CSG здесь **не проверяются**.

## 7. Исправление после независимого аудита A0 · P2-A0-01

**Исторический результат первых 6 проверок выше не изменён.** На [исходном HEAD](https://github.com/netkeep80/fgm-platform/pull/74#issuecomment-7095742699) независимый аудит установил `BLOCK · P1=0 / P2=2 / P3=0`. Попарное сравнение глубин с допуском `EPS` образовывало цикл выбора A→B→C→A, делая победителя зависимым от порядка.

### 7.1 Новый математический контракт

Для конечных мировых `hit` принят строгий детерминированный ключ с приоритетом:

1. **Численная глубина `t` без допуска** — меньшая глубина выигрывает. `NaN` и бесконечность отвергаются.
2. **При равных в точности глубинах** больший безопасный целочисленный приоритет выигрывает.
3. **При равных глубине и приоритете** ID сравнивается по кодовому порядку строки.
4. **При равных предыдущих полях** грани сравниваются по фиксированному порядку `0- < 0+ < 1- < 1+ < 2- < 2+`.

Для поддерживаемого класса допустимы только валидные `face` вида `^[012][+-]$`. Допуск `1e-9` остаётся **только** для проверки совпадения двух независимо вычисленных численных глубин. Строгий порядок конечных ключей исключает нетранзитивность, присущую исходному отношению близости. Это решение **не подтверждает** численную стабильность или одинаковый `t` в реальном GPU — там потребуется отдельный глобальный depth/quantization ABI.

Оракул `O-H` теперь использует отдельную реализацию arbitration, а `candidate` — строгое сравнение `compareHit`. Сохраняются общие мировые лучи и ограниченные аналитические поверхности; полной математической независимости всех компонент нет.

## 8. Независимый новый P2-A0-03 — границы аналитического параллелепипеда

**Текущий статус на 23.11.2026: исправлено в исследовательском коде, независимо НЕ принято.** [Независимый delta-аудит исходного HEAD](https://github.com/netkeep80/fgm-platform/pull/74#issuecomment-7097244377) установил `BLOCK · P1=0 / P2=1 / P3=0`: исходные P2-A0-01 (транзитивность) и P2-A0-02 (владение) независимо закрыты, но обнаружено новое `P2-A0-03` — ложное пересечение при использовании допуска `EPS` для расширения границы.

### 8.1 Геометрическая политика и исходный контрпример

Для ограниченного класса тестового стенда выбран **замкнутый точный аналитический AABB** в конечной арифметике JavaScript. Координата ровно на границе считается принадлежащей параллелепипеду; любое строго внешнее значение — нет. Пересечение должно иметь параметр луча **`t>0`**. Для строго нулевой компоненты направления используется проверка параллельности, для сколь угодно малой ненулевой — вычисление пересечения. В slab проверяется **`near>far`**, а в face-кандидате — **`lo[i]<=p[i]<=hi[i]`**, без расширения допустимой поверхности и без допуска в положительности луча.

Введённая константа `VERIFY_DEPTH_EPS=1e-9` применяется **исключительно** к независимому сравнению вычисленной глубины и исторической демонстрации ошибочного fuzzy-компаратора. Она **не** расширяет границы, не меняет пересечения интервалов и не выбирает победителя. Строгий ключ глубины/приоритета/идентичности из P2-A0-01 сохранён.

**Негативный случай, ранее приводивший к ошибке:** куб `[-1,1]^3`, исходная точка `(-2,1+0.5e-9,0)`, направление `(1,0,0)`. Ожидается **MISS** по обоим алгоритмам; старая проверка face ошибочно принимала точку `(-1,1+0.5e-9,0)`. Исправлены также прежние некорректные допуски `near>far+EPS` и `abs(direction)<1e-14`.

### 8.4 Дополнительная погрешность округления и точные двоично-рациональные предикаты

**Отрицательное обнаружение после первой версии исправления:** самостоятельная детерминированная проверка **110 000** лучей, проходящих рядом с углом параллелепипеда на расстоянии порядка одного `ULP`, выявила **3 620** расхождений hit/miss между формально строгими, но *раздельно округлёнными* slab- и face-вычислениями. [Уточнённый протокол до изменения кода](https://github.com/netkeep80/fgm-platform/pull/74#issuecomment-7097802630) установил единый математический смысл: **каждое конечное двоичное значение IEEE-754 интерпретируется как точное двоично-рациональное число**. При потенциально неоднозначном результате сначала используется безопасная числовая оценка для отделения бесспорных случаев, затем **BigInt**-проверка строгого порядка параметров и принадлежности исходной грани.

Для slab вычисляется порядок пересечений трёх интервалов. Для face проверяется пересечение *каждой исходной мировой плоскости* с ограничивающими координатами посредством целочисленных перекрёстных произведений. Два метода **не вызывают друг друга** и не используют общий результат попадания; общим является только точное декодирование входных double и арифметика двоичных рациональных чисел. Конечное представление глубины `t` для тестового контракта остаётся `Number` и должно быть представимо. Выбор ближайшей поверхности сохраняет прежний строгий порядок ключей P2-A0-01. Допуск `VERIFY_DEPTH_EPS` не вводится в геометрическую принадлежность.

## 9. P2-A0-04 — строгий глобальный first-hit при округлении двух различных глубин

**Дата 23.11.2026.** [Независимый аудит исходного HEAD](https://github.com/netkeep80/fgm-platform/pull/74#issuecomment-7100698970) завершился **BLOCK P1=0/P2=1/P3=0**. Исходные P2-A0-01/02/03 независимо закрыты, но найден новый P2-A0-04: различные точные параметры луча `t_A=1`, `t_B=1+2×Number.EPSILON/5` округлялись к одинаковому `Number t=1`, из-за чего priority объекта B ошибочно замещал ближайший объект A.

[Пререгистрация до правки](https://github.com/netkeep80/fgm-platform/pull/74#issuecomment-7101054834) фиксирует допущения, исправление, независимость и тесты.

### 9.1 Уточнённый численный контракт

- Каждое геометрическое пересечение несёт дополнительный **точный ключ глубины**: исходные конечные `origin[axis]`, `bound[axis]`, `direction[axis]`, преобразуемые в точное двоично-рациональное `t=(bound-origin)/direction`. Параметр `t:Number` сохраняется только как приближение для отчёта и визуализации; его округление **никогда** не делает две глубины равными для выбора видимого ID.
- Межобъектные и межобластные сравнения используют **`BigInt` cross-multiplication точных рациональных глубин**. Приоритет, ID в ASCII-порядке, а затем каноническая грань разрешают **только действительное равенство** точных глубин. Для самостоятельных synthetic hits без source-тройки значение `Number t` означает точное двоично-рациональное значение.
- `slab` сохраняет независимое вычисление пересечения трёх интервалов, `faces` — проверки шести **исходных мировых граней**. Глобальные свёртки `oracleBetter` и `compareHit/better` кодируются раздельно; общий только декодер float64 и представление точной дроби. Никакой `EPS` не используется при выборе глубины.
- Точка `faces().p` — **округлённая диагностическая координата**, не физически точный world-point. Новая `exactBucketCoord` назначает каждое пересечение в одну из 1/8/64 synthetic областей на основе точной рациональной позиции `o+d*t` и границ `[-4,4]^3`, а не по `p`. Все области сворачиваются без culling, поэтому это **не** подтверждение сертифицированного выбора физических фрагментов FGM/GPU.

### 9.2 Сохранённые отрицательные и новые положительные свидетельства

Исходный A/B контрпример отдельно воспроизведён на **предыдущем** source Git blob `cafa89186dfc8c0cabefa5e71f03911174abbfc7`: oracle и candidate во всех 1/8/64 возвращали ошибочный ID B. Точная дробь A меньше B, хотя оба приближённых `t` равны 1.

На новой версии исходного файла `r0-preflight.mjs`, Git blob **`6dcbc06232fa2feecfc1247fdb8214bab24f874b`**, SHA-256 **`e5d414c2945f47e5c98d60dac47f9ace4295cd58847dead5e60545f4089e7f0d`**, размер **26 648 байт UTF-8**, в самостоятельной **V8**-проверке с Node API stubs результат **9/9 PASS**. Это **не полноценное выполнение файла под Node.js** и не независимый аудит. Новая девятая группа:
